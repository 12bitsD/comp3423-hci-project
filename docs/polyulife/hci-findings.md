## F-ROOM-EMPTY-QUERY：清空输入后，旧结果的归属需要更明确

**用户目标与起点。** 已尝试查询房间、得到无结果反馈后，清空输入并准备重试。实际起点是 Tue 29-Sep 选中、先前 `PQ604B` 查询显示 `No room found`。

**观察事实。** `A-ROOM-CLEAR` 清空房间字段后，截图仍显示 `No room found / Please search another room.`，没有显示这条结果属于先前哪个已提交房间号。随后 `A-ROOM-EMPTY-SEARCH` 点击空输入的搜索按钮，页面恢复 `Find an available classroom / Enter room number to begin search`。对应 `S-CLEARED → S-EMPTYQUERY`。

证据：[E-CLEARED：空输入与旧无结果文案](../../evidence/2026-09-28-full-audit/room-135506-input-cleared.png) → [E-EMPTYQUERY：空搜索后恢复提示](../../evidence/2026-09-28-full-audit/room-135521-empty-query.png)。截图时间分别为 13:55:06、13:55:21 UTC；这不是两种状态的持续时长测量。

**问题假设。** 用户可能把当前空白输入与下方旧反馈视作同一查询状态，无法确认清空是否已生效，因而多做一次搜索或再次编辑。当前没有真人误解、重复点击或任务失败证据。

**反证和边界。** 系统有明确的初始输入指导；空搜索可以恢复该状态，所以不能写成“没有清空机制”或“无结果后无法重试”。后续输入 `A`、选择 `AG206` 已返回有效结果，说明查询路径可恢复。保留上次已提交结果也可能是有意采用的“编辑后再提交”语义，不能仅凭保留结果判定程序错误。

**HCI 原则。** 系统状态可见性：编辑中的查询与已提交查询应当能被区分，否则用户需要从记忆推断结果归属。

**设计建议。** 比较两种可选方案：清空房间字段时恢复初始引导；或保留结果但标注其已提交查询，例如“未找到 PQ604B；当前输入尚未查询”。先确认查询语义，再选一种一致实现。不要在忠实复现版中悄悄把建议替换成真实行为。

**待验证。** 重走“无结果 → 清空”和“成功结果 → 修改但不提交”，确认规则是否一致；真人任务中让参与者说明当前结果对应哪个房间，以及下一步会如何重试。观察是否出现误判后，才讨论影响程度。

## F-ROOM-DATE-ASYNC：新日期选择与旧结果之间存在过渡状态

**用户目标与起点。** 查看同一房间另一天的可用时段；起点为 AG206、Tue 29-Sep、Available。

**观察事实。** `A-ROOM-DATE-DRAG` 将日期条拖至 Sun 04-Oct 可见后，`A-ROOM-DATE-SUN` 选择该日。[E-SUNTRANSITION](../../evidence/2026-09-28-full-audit/room-140117-sun-selected-old-result.png) 同时显示高亮的 Sun 04-Oct，以及结果区的 `29-Sep (Tue)` 和六个绿色时段。随后无需再次点击搜索，[E-SUNEMPTY](../../evidence/2026-09-28-full-audit/room-140214-sun-no-available-room.png) 的结果日期更新为 `04-Oct (Sun)`，显示无可用状态。对应 `S-SUNTRANSITION → S-SUNEMPTY`。

**问题假设。** 如果过渡期间用户主要看顶部高亮日期和时段，可能把旧时段当作新日期的数据。现有证据只确认出现过这种组合，不能确认用户会误读，也不能确认它出现得足够久而影响任务。

**反证和边界。** 结果区自身仍明确标注 `29-Sep (Tue)`，不是完全没有数据归属信息；后续确实自动更新，因此“日期不能切换”“必须再次 Search 才生效”均与证据相反。静态截图中未见独立加载提示，不代表整个过渡过程没有动画或反馈。两次观察的时间差、截图文件名或 Agent 等待均不能用于估算请求延迟。

**HCI 原则。** 系统状态可见性与反馈：筛选已改变、请求进行中、结果已对应新条件，应能被清楚区分。

**设计建议。** 改版候选可显示“正在查询 AG206 · 4 Oct”，并暂时弱化旧列表；若保留旧结果，应标注“上次结果：29 Sep”。请求成功后同步更新结果日期和时段。这里不预设一定要新增加载动画，先核实现有反馈是否足够。

**待验证。** 用连续取证重走一次日期切换，确认是否有 spinner、占位状态或已提交日期提示；再检查快速连续切日期时的最终结果是否对应最后选择。真人任务中检验能否正确说出当前时段所属日期。当前不做延迟、竞态故障或数据错误结论。

## H-ROOM-NO-AVAILABILITY-RECOVERY：无可用时段后的指引可以更贴近当前筛选

**用户目标与起点。** 在所选日期找到可以使用的教室；起点是 AG206、Sun 04-Oct、Available。这是房间已识别后的无可用状态，不同于输入 `PQ604B` 得到的 `No room found`。

**观察事实。** [E-SUNEMPTY](../../evidence/2026-09-28-full-audit/room-140214-sun-no-available-room.png) 保留 AG206、04-Oct、日期条和 ALL / Available 控件，主反馈为 `No available room / Please search another room.`。该消息区域没有单独的改日期或重试按钮。`A-ROOM-SUN-ALL` 随后成功切到 ALL，[E-SUNALL](../../evidence/2026-09-28-full-audit/room-140253-sun-all-unavailable.png) 可见时段为红色；更多滚动记录仍未确认列表的真实末端。

**问题假设。** “No available room”可能被理解为“该房间无可用时段”或“整个搜索范围都没有房间”，而指引只建议换房间，未显式说明当前日期和 Available 筛选的作用。部分用户可能放弃同一房间其他日期的查询，或不知道下一步如何缩小问题。尚无真人理解和放弃行为证据。

**反证和边界。** 房间号、结果日期、筛选和可编辑输入仍然可见；切回 ALL 已成功，页面不是不可恢复的死路。现有证据也没有证明该日确实应该有可用时段，不能把正常空数据写成查询失败。ALL 截图及滚动没有穷尽全部时段，不能独立据此声称“全天都被预约”。

**HCI 原则。** 状态说明与用户目标匹配、用户控制和自由：空结果应说明范围，并帮助用户选择下一次有效查询。这不是把正常“无可用”归类为系统异常。

**设计建议。** 文案候选为“AG206 在 4 Oct 没有可用时段”，并提供“换日期”“搜索其他房间”入口；保留 ALL 供查看时间表。若未来建议邻近日期或其他房间，必须来自真实可用数据；原型假数据要明确标注，不能暗示目前 App 已有此服务。

**待验证。** 从该状态实际完成“换日期恢复可用”与“换另一有效房间”的闭环；确认不可用的业务含义（已占用、关闭、不可预约等），再决定是否可展示原因。真人任务中先询问如何解释此文案、准备选择哪一步，不预先提示新增按钮。

## F-ROOM-PREVIEW-CONTEXT：Preview 到达房间内容的路径值得比较，返回上下文已保留

**用户目标与起点。** 查询到 AG206 可用时段后，查看该房间的照片或设施。起点为 AG206、29-Sep、Available。

**观察事实。** `A-ROOM-PREVIEW` 打开标题为 `Room Search` 的内嵌网页。加载后首张可读截图 [E-PREVIEWTOP](../../evidence/2026-09-28-full-audit/room-preview-135826-top.png) 主要显示校方站点标识、Information Technology Services Office、校园图片和 Learning and Teaching Technology Support 标题，尚未显示 AG206。向下滚动后，[E-PHOTO1](../../evidence/2026-09-28-full-audit/room-preview-135905-ag206-photo-1.png) 显示 `Room : AG206` 和照片。Next 已切换照片；关闭内嵌页后，[E-RETURN](../../evidence/2026-09-28-full-audit/room-140021-preview-return-available.png) 保留 AG206、Tue 29-Sep、Available 及对应时段。

**问题假设。** 对“查看当前房间”的目标，首先看到通用站点内容可能削弱“已到达目标”的确认，需要额外寻找或滚动。标题 `Room Finder → Room Search` 的变化也可能要求用户重新判断页面用途。没有证据表明用户已迷路，或这次滚动显著增加任务成本。

**反证和边界。** Preview 本身带向外箭头，内嵌页有官方域名、关闭按钮和浏览器控制，提供了页面切换线索。AG206 内容确实存在且照片可切换，返回上下文也已保留；不能写“Preview 打错页面”“找不到目标房间”或“返回丢失筛选”。不应简单删除通用说明，因为其用途、其它房间内容和下方设施信息尚未完整检查。

**HCI 原则。** 系统与用户目标匹配、识别优于回忆、用户控制和自由：优先确认当前房间，并保留离开及返回能力。

**设计建议。** 比较直接定位到 `Room : AG206` 的锚点与当前顶部进入方式；在内嵌标题或入口明确“AG206 照片与设施”。保留查看完整官方页面的路径，并保留已验证的房间、日期、筛选返回状态。忠实复现应保留原始网页顶部及滚动路径；优化候选使用独立帧或页面并标注设计差异。

**待验证。** 重开 Preview 确认初始滚动位置是否稳定；检查照片下方设施信息、PDF 和轮播边界；验证改锚点不会遗漏重要警示或导致返回异常。真人比较可记录首次确认房间位置的行为和原话，真实耗时由实际测试取得。

## 进入设计与评估前的处理

本页先保留 Room 的四项有证据起点的研究主题，以及下文虚拟助手的布局稳定性、设置名称与 Calendar 辅助访问待核实主题，不打未经评估的严重度分数。清空输入与 Preview 路径适合先做小范围方案比较；日期反馈必须补连续观察，才能决定是否确有缺口；空状态恢复需要补完整重试路径和业务含义。研究主题数量不等于课程要求的主要功能数量。

Figma 的原状复现以 [coverage.json](coverage.json) 的已观察状态和真实动作结果为准，单独保留上文建议为改版候选。日期过渡不可被误连成永久错误，Preview 返回不可丢掉已证实保留的上下文，信息卡片不能无依据改成预约提交。未观察的网络、错误、轮播末端和外部跳转状态明确标为待验证，不能用设计推测冒充既有 App 行为。

后续真人评估应分别验证结果归属、日期归属、空状态下一步和 Preview 目标识别；先记录真实行为及原话，再判断假设是否成立。涉及手机触控、单手可达性、设备定位或无障碍辅助技术的结论，须补真实设备或对应辅助技术测试。本页目前没有这些结论。

## H-ASSISTANT-LAYOUT-SHIFT：后出现的头图会移动聊天入口

**用户目标与起点。** 从 More 打开 Virtual Assistant，准备通过文章中的 `here` 进入聊天网站。

**观察事实。** 15:46:04 的[首个详情截图](../../evidence/2026-09-28-full-audit/virtual-assistant-154604-before-hero.png)在标题上方没有头图。15:46:16 的[后续截图](../../evidence/2026-09-28-full-audit/virtual-assistant-154616-hero-loaded.png)增加 “May I help you?” 配图，标题和 `here` 下移。按照前一布局坐标尝试点击时仍停留详情；根据新截图定位 `here` 后，实际进入 `comp-chatbot.polyu.edu.hk` 的 Disclaimer，再经 ACCEPT 到 Welcome。对应 `S-ASSISTANT-BEFORE-HERO → S-ASSISTANT-DETAIL → S-ASSISTANT-WEB-LOADING → S-ASSISTANT-DISCLAIMER → S-ASSISTANT-WELCOME`。

**问题假设。** 正在阅读或准备点击的用户可能需要重新定位链接。头图占用空间从无到有会改变目标位置，但目前一次 Agent 坐标尝试只证明本次操作需要重新定位，不能当作真人误触、阅读中断或任务耗时数据。

**反证和边界。** 链接最终可见且可用，没有证据支持“聊天入口打不开”。截图不是连续视频，不能量化头图等待时长、变化持续时间或出现频率；也未比较缓存状态或手机端。头图有已验证的展开和关闭功能，不能无理由删除它。

**HCI 原则与建议。** 位置稳定性及错误预防：可比较预留头图固定空间、加载占位与目前布局。改版候选应保留图片展开和返回能力；忠实复现仍保存头图前后两个真实状态，不把待比较的优化写成原 App 已有行为。

**待验证。** 连续记录冷启动与重复打开，确认空间是否稳定预留、链接是否持续可点击；在真人“进入虚拟助手”任务中观察是否需要重新寻找入口。另行核实 Welcome 输入区与当前 Mac 视口的适配，不能把目前网页输入卡点归因给头图变化。
